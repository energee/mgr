## Decisions

- 2026-07-13T03:35Z — Ruled out a missing unique constraint on `beer_styles.name` (would make `onConflict: "name"` fail on every single call) after finding `UNIQUE(name)` as a table-level constraint in `00011_catalog_and_recipe_junction.sql:35` — easy to miss with a naive grep for `name.*UNIQUE`.
- 2026-07-13T03:40Z — Landed on the root cause: `upsertRows()` batches up to 50 rows into ONE `.upsert(batch, { onConflict })` call, i.e. one `INSERT ... ON CONFLICT DO UPDATE` statement. Postgres rejects that whole statement — "ON CONFLICT DO UPDATE command cannot affect row a second time" — if two rows in it share an onConflict-key value. `beer_styles`/`brands`/`vessels` upsert on `name` (all `TEXT ... UNIQUE` per `00011_catalog_and_recipe_junction.sql`, `00003_brands.sql`, `00006_vessels.sql`), and the source Mongo collections have no uniqueness guarantee on `name` — a very plausible, deterministic, recurring failure on legacy hand-maintained brewery data, matching the 24-events-in-14-days pattern (same duplicate re-triggers on every sync).
- 2026-07-13T03:45Z — Fix scope: a single generic fix in `upsertRows()` (dedupe by onConflict key before chunking) covers all 14 entity syncs at once, rather than patching individual entity functions.
- 2026-07-13T04:05Z — `/simplify` and `/code-review:code-review` skills both errored (`Execute skill: <name>`) every retry — appears broken in this session/environment. Did a manual simplify pass myself (found `[...arr].reverse().find()` → `arr.findLast()`, and a redundant length assertion in the new test; both fixed) and substituted an independent review by dispatching a fresh general-purpose subagent with no prior context, asked to adversarially check the diff.
- 2026-07-13T04:10Z — The independent review caught two real issues I would not have found via a plain `git diff` (it silently rendered as "Binary files differ"): (1) a stray literal NUL byte had been written into the source at the `.join(" ")` call — a tool/encoding artifact, not something I typed intentionally — fixed via a byte-level Python replace since the Edit tool's string matching couldn't target the NUL byte directly; (2) the original `dedupeByConflictKey` gated dedup on *every* row having the onConflict column, so one row missing it (e.g. a legacy doc with no `name`) would silently exempt the *entire* batch from dedup, letting the real bug recur. Rewrote it to make that decision per-row: rows missing the conflict column pass through untouched, rows that have it get deduped normally.
