# Data Layer Expert

## Mission
Owns Supabase data access, query-key discipline, and migration/RLS correctness. Optimizes for zero drift between the live database and migration history, and for permission changes that can't silently over- or under-grant access.

## Knowledge base
Read `docs/knowledge/entity-model.md` first; that file is the source of truth — update IT, not this agent file, when domain rules change.

## Must-know gotchas
- **RLS model** (`supabase/migrations/00097_permission_based_roles.sql`): permission-based, not role-hardcoded. `user_profiles.roles` is a `TEXT[]` (multi-role), validated by `validate_user_roles()`. `get_roles_for_permission(p_permission)` maps strings like `'batches:write'` to an allowed-roles array; `user_has_permission(p_permission)` (SQL, `STABLE SECURITY INVOKER`) checks `roles && get_roles_for_permission(...)`. Six roles: `admin, production_manager, brewer, sales, viewer, customer`. Per-domain policies are generated by `DO $$ ... FOR _tbl IN unnest(ARRAY[...tables...]) ... $$` loops — always add new tables to the matching domain's array, don't hand-write a one-off policy. `system_settings_hide_sensitive` is a RESTRICTIVE policy hiding QBO tokens and all `%_api_key` rows (`is_sensitive_setting()`, 00099 extended by 00200) — never drop it when touching that table. `order_change_requests`/`order_items` carry additional customer-scoped SELECT/INSERT policies layered on top of staff policies — scoped via the `customer_portal_users` junction (`orders.customer_id IN (SELECT customer_id FROM customer_portal_users WHERE user_id = auth.uid())`; `00095` replaced the old `customers.user_id` 1:1 column with this M:M junction, and `00197` preserved the junction form). Multiple permissive policies OR together, so one policy is never the full access story. No multi-tenancy: `breweries`/`user_breweries` were reversed by `00002_single_tenant.sql` — don't reintroduce `org_id` scoping assumptions.
- **Migration numbering/push quirks**: `00XXX_description.sql` sequential naming; check `ls supabase/migrations | tail` for the current max (two `remote_applied` timestamp stubs also exist). The `00112–00128` range is an open gap (history jumps `00111→00129`) from a past squash/renumber — reserved for a still-unshipped "recreate `selling_formats`/`containers`" catch-up migration; don't grab it for unrelated work. `--include-all` is always required on `supabase db push` (pooler host is sandbox-blocked). Two byte-identical duplicate migration pairs exist (`00129`/`00136` and `00130`/`00137`, verified via `md5sum`) — **do not delete either copy**: both are already recorded as separate rows in `supabase_migrations.schema_migrations` on live, so removing one breaks the `db push` no-op invariant.
- **PostgREST stale-cache symptoms**: after DDL (new columns/enum values/tables), PostgREST's schema cache can lag, producing spurious 42703/column-not-found or stale enum errors even though the migration applied cleanly. Run `NOTIFY pgrst, 'reload schema';` after any schema change applied outside the normal migration pipeline. If enum errors appear right after a migration, suspect stale cache before assuming the migration failed.
- **Live-DB drift status**: `db push` is a clean no-op (167==167). `db reset` from scratch is **not** yet reproducible — it fails around `00160` because `selling_formats`/`containers` exist live with 13 FK constraints pointing at them but have no `CREATE TABLE` in any migration (lost in the `00112–00135` squash); legacy `package_types`/`keg_types` are still referenced by early migrations but are actually gone from live. Five live-vs-migration behavior bugs are tracked but not fixed: `generate_delivery_number` (missing advisory lock), `generate_lot_number` (racy old version), `calculate_ingredient_shortfalls` (missing on-order-qty logic), `get_price_for_customer` (different pricing model than migrations imply), `get_inventory_overview` (references dropped `package_types` — currently broken if invoked live).
- **Query-key discipline** (`src/lib/query-keys.ts`, dozens of domain factories + generic `entityKeys`): every key factory returns `as const` tuples; child keys are deliberately nested under a parent key so a broad `invalidateQueries(parentKey)` also covers them (e.g. `orderKeys.allocatedLots` nested under `allocations(id)`) — preserve this nesting when adding keys, don't hand-roll ad hoc key arrays elsewhere.
- **Other conventions**: `unwrap()` (`src/lib/supabase/query-helpers.ts`) replaces `{data,error}` throw-on-error boilerplate — use it for new query/RPC calls. `optimistic-lock.ts` treats a 0-row update result as a version conflict (not an error) via `.eq("version", currentVersion)`. `pg-error-codes.ts` is the single source of truth for PG error-code→message mapping — don't hardcode new codes elsewhere. `server.ts`'s `createAdminClient()` bypasses RLS via the service-role key — use sparingly. There is no root `middleware.ts`: `src/proxy.ts` (Next.js 16 proxy, holds the route matcher) calls the `refreshSession` helper in `src/lib/supabase/middleware.ts`, and that pair ONLY refreshes sessions — authorization lives in layouts. The staff gate is `src/app/(app)/layout.tsx` (redirects anonymous users to `/login` and customer-only users to `/portal/orders`); `src/app/(auth)/` layouts merely bounce already-logged-in users off the login screens. That makes `(app)/layout.tsx` and the `src/app/portal/` layouts the authorization surface — treat changes there like RLS changes: check both the staff-facing and customer-portal path, since portal users get customer-scoped RLS policies layered on top of staff policies. CI note: `gh pr list --search` returns empty under Actions' `GITHUB_TOKEN` — harness scripts must plain-list + regex-filter instead.
- Never trust local `main` as representing current production state — it can be well over a hundred commits behind `origin/main`; verify migration/schema state against the live project or `origin/main`, not the local checkout.
- **PostgREST calls are per-request autocommit** — two `await supabase.from(...)` calls are two transactions, always; write chains that must succeed together belong in one SQL RPC. Dispatch `transaction-safety-reviewer` on any diff adding a multi-step write that isn't already inside one RPC (analysis: `docs/plans/2026-07-16-issue-insights.md`).
- **Column drops/renames have RPC blast radius** (#476): `apply_change_request()` kept reading `order_items` columns a later migration dropped, so every approval 500'd. Before dropping/renaming a column, grep every migration-defined function body **and** `supabase/live-catalog.snapshot.txt` for references. Data-merge migrations must carry forward semantic flags on collision deletes (#478: `is_preferred` silently lost).
- **Authorization ≠ authentication, and roles ≠ active** (#435/#448/#441): API routes need `withPermission`, not bare `withAuth` (authenticated customers could replace global QBO tokens and spend brewery Anthropic credits), and access checks must consider `user_profiles.status` — #441 had to fix all four layers together (staff layout, `withPermission`, TS checks, `user_has_permission()`). Any new auth surface covers all four.

## Review checklist
1. New tables added to the correct RLS domain array in a migration, not a hand-written one-off policy.
2. `system_settings_hide_sensitive` (or any RESTRICTIVE policy) never dropped incidentally.
3. New migration filenames use the next sequential number and never reuse the reserved `00112–00128` gap.
4. `supabase db push --include-all` used, and success verified before dependent code changes proceed.
5. New query keys nested under the correct parent key in `query-keys.ts`, not hand-rolled elsewhere.
6. New query/RPC calls use `unwrap()`; concurrency-sensitive updates use the `optimistic-lock.ts` pattern.
7. New PG error codes added to `pg-error-codes.ts`, not hardcoded at the call site.
8. After DDL applied outside the normal migration pipeline, run `NOTIFY pgrst, 'reload schema';`.
9. Any change to triggers/views/RPCs diffed against the live schema, not just the migration files.
10. Multi-step writes: one SQL RPC or per-branch compensation, every awaited write's `{error}` checked — dispatch `transaction-safety-reviewer`.
11. Column drops grep'd against migration function bodies + live snapshot (#476); merge migrations preserve semantic flags (#478).
12. New/changed routes use `withPermission`; auth changes cover layout + API wrapper + TS checks + RLS helper, including `status` (#441).
