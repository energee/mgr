- **2026-08-12 (required status checks for `main`).** Made `Database Lint and Integration Tests` eligible as a required status check (#713) by **deleting** `db-lint.yml`'s `paths:` filter, so the job that carries the required name runs on every PR and reports its own result. A `paths:` filter on `on:` cannot back a required context: GitHub never queues the workflow for a filtered-out PR, so the check stays absent and a docs-only PR is unmergeable forever. Required set: `Static Checks`, `Unit Tests`, `E2E Tests`, `Database Lint and Integration Tests`. `Production Build` must never be added — it is schedule-gated and would leave every PR pending. `shell-lint.yml` stays path-filtered and advisory. `docs/agents/ci.md` gains a Required status checks section; `.github/scripts/ci-workflows.test.ts` pins the invariant (no `paths:` filter, exactly one job with the required name, no job-level `if:`, no `needs:`, no `continue-on-error:`, and `Production Build` still schedule-gated), mutation-checked by reintroducing a filter and an `if:` — each reds the suite. An always-reporting gate job around a retained filter was built first and discarded: it cost +157 lines against a nine-line deletion for the same guarantee, and it introduced a bug of its own — `on: paths:` globs and git pathspecs are different dialects, and `supabase/migrations/**/*.sql` as a pathspec requires a directory component, so it matched **0 of 264** flat migrations and every migration PR would have reported the required check **green**. Caught only by executing the patterns; the reasoning had concluded the opposite. The measurement that settled it: db-lint is ~3m13s against `E2E Tests` at ~5m50s on every PR anyway, so it was never the critical path #713 assumed. Also documented two harness footguns in `docs/agents/gotchas.md` — #786 (the pre-PR gate is a `PreToolUse` hook, so `touch … && gh pr create …` can never pass; its git-dir resolution is per-worktree and **correct**, contrary to the issue text; its matcher has no shell-quoting awareness) and #785 (`/code-review` and `/simplify` have no repo-side definition, so nothing here can scope them to a worktree — not repo-fixable) — plus the `make check | tail` trap, where a pipe masks a failing build behind `tail`'s exit code.
