- **2026-07-13 (SENTRY-7597067722 — Failed to fetch notifications; branch `sentry-fix/SENTRY-7597067722`).** Root cause: `src/lib/supabase/client.ts`'s `createClient()` built a brand-new Supabase browser client (and internal GoTrueClient) on every call rather than reusing one instance. It's called fresh in 145+ client components/hooks across the app, including on every re-render of `NotificationsProviderInner` (`src/contexts/notifications.tsx:109`). Every instance shares the same auth storage key, so concurrent `GoTrueClient`s raced over the same `navigator.locks` name — a newer instance's lock acquisition could "steal" the lock from an older instance's in-flight `supabase.auth.getSession()`/`getUser()` call, aborting whatever request (like the unread-notifications fetch) was waiting on it, producing exactly `AbortError: Lock broken by another request with the 'steal' option`. Fixed by making `createClient()` a module-scoped singleton — Supabase's own documented remediation for this class of bug. Pattern scan found no other non-singleton client factories (the server-side `createClient()` in `src/lib/supabase/server.ts` is correctly per-request, tied to per-request cookies, and was left untouched). Regression test added (`src/lib/supabase/__tests__/client.test.ts`) confirmed to fail pre-fix (each call returned a distinct instance) and pass post-fix (all calls return the same instance, underlying factory invoked once). Full suite (2291 tests), typecheck, and lint all clean.
