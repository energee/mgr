- **2026-07-14 (make PO receiving atomic — closes the last #412 defect).** Receiving against a purchase order was a multi-step client write with no transaction: the `po_receives` rows were inserted *before* the status was read and validated, so receiving against a `draft` PO recorded the receipt and then threw on the illegal transition, leaving the rows behind with nothing to roll them back. Migration `00245_receive_purchase_order_items.sql` moves the whole sequence — lock the order, reject over-receipts, insert the receipts, decide `partial`/`fulfilled`, validate the state-machine transition, write the status — into one `SECURITY INVOKER` Postgres function, so it commits or aborts as a unit. `SELECT ... FOR UPDATE` on the order serializes concurrent receipts, which also closes a hole the TypeScript version could not: the status was previously decided from reads taken outside any transaction, so a concurrent receipt could commit a status computed from stale numbers — passing a client-decided status into the function would have been atomic but still wrong. The function is now the **single source of truth** for the fulfilled/partial rule; `src/domain/purchasing/po-receipt-status.ts` and its tests are deleted, and `po-receiving-service.ts` is a thin `supabase.rpc` wrapper. Quantities are `DECIMAL(10,4)`, so SQL sums exactly and the float-epsilon workaround is gone with them. The component test now covers the RPC boundary (payload, returned status, error propagation) rather than re-testing rules that live in SQL; `makeSupabase` gained optional `rpc` queues. Suite 2343 passing / 157 files; `tsc` and lint clean. **Migration is NOT yet applied to the live database** — run `scripts/db-push.sh`.
