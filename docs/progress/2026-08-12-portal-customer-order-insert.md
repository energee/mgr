- **2026-08-12 (portal customers can place orders — RLS half).** Phase 4 node C1. The portal was read + lock only: a customer could read their own orders (00276) and amend a staff-created one through `submit_order_change_request()` (00264), but there was **no customer INSERT policy on `orders`** anywhere in the chain. Migration `00290_portal_customer_order_insert.sql` adds `orders_customer_insert` and `order_items_customer_insert`, deliberately over-constrained: `customer_id` bound to the caller's own customer through the revocation-aware `customer_portal_users` join, `status` pinned to `draft` (the staff-confirm state, enforced in the policy rather than the UI — the portal writes through PostgREST with the user's own JWT, so there is no server route in between), `scheduled_date`/`fulfilled_date`/`is_export` pinned unset, and `order_items.unit_price` required NULL so pricing stays server-side via `get_price_for_customer` (`src/services/pricing-service.ts`) at staff confirm. **Shape was an operator decision** — an atomic staff-confirm RPC mirroring 00264 was recommended and a scoped INSERT policy was chosen instead; the concern (this widens the portal's write surface against a core sales table) is recorded in the migration header and `docs/plans/2026-08-12-phase-4-rebaselined.md`. **`generate_next_order_number()` had to become SECURITY DEFINER:** `generate_next_number()` (00142) scans the target table for the series max and is SECURITY INVOKER, so under portal RLS it sees only the caller's own orders and returns an already-taken number — a UNIQUE violation on nearly every portal order. `orders.order_number` gained a DEFAULT so the portal never supplies one; staff forms keep prefilling explicitly and are unchanged (both paths verified against the local stack). 15 behavioral integration tests in `src/__tests__/integration/portal-order-insert-rls.test.ts`, one per constraint plus positive controls — the positive controls are what make the denials meaningful, since before 00290 every insert was denied for want of any policy at all. `make check` green (2960 tests). **Not applied to live** — awaiting the operator. **Plan corrections:** the next migration number was 00290, not 00289 as the plan stated (00289 had already landed); and the plan did not anticipate the order-number generator problem, which any customer INSERT path hits.
