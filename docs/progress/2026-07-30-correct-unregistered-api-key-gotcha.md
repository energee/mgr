- **2026-07-30 (correct the `Unregistered API key` gotcha).** PR #651 documented this failure mode with a mechanism that is false — that `supabase start` / `make db-local` "can rotate its JWT keys" — so the entry in `docs/agents/gotchas.md` and the `scripts/db-local.sh` message were rewritten. Verified instead: `supabase/config.toml` sets no `[auth]`/JWT override, so the CLI signs local keys with its own hardcoded default secret and an older local key still verifies — local keys do not rotate on restart; the hosted gateway rejects an unregistered key with `Invalid API key` (`sb-error-code: UNAUTHORIZED_INVALID_API_KEY`), and Kong 2.8.1 (the CLI's local gateway image) with `Invalid authentication credentials`, so neither emits `Unregistered API key` and the "local Kong" attribution repeated across #636–#642 is unsupported; and Sentry's `environment` comes from `NODE_ENV` (`src/lib/sentry-config.ts`), so it cannot tell you which Supabase instance a credential targeted. The entry now gives a diagnostic procedure — identify the instance in `NEXT_PUBLIC_SUPABASE_URL`, compare the key against that instance, reproduce with `curl` — instead of asserting one cause, and drops the self-falsifying "appears nowhere in this repository" line. `scripts/db-local.sh` now tells you to resync `NEXT_PUBLIC_SUPABASE_URL` too, which matters because `.env.example` ships a hosted URL and `createAdminClient()` pairs the URL and the service-role key from two independent env vars that nothing cross-checks.
