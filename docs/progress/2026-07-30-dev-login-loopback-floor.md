- **2026-07-30 (dev-login's `E2E_DEV_LOGIN` path now requires a loopback database, resolved through the admin client's own accessor — issues #656/#679, branch `fix/656-dev-login-loopback-floor`).** `/api/auth/dev-login` mints a full admin session with no caller credentials, and its only negative floor was `VERCEL_ENV` — absent entirely off Vercel (self-hosted Docker, Fly, Railway) and absent on Vercel when "Automatically expose System Environment Variables" is off, so the floor is a silent no-op there and the flag alone was the whole gate. Fixed by requiring, on the flag path, that the Supabase project URL have a loopback hostname (`localhost`, `127.0.0.1`, `[::1]`), compared after `new URL()` parsing rather than by substring so `https://localhost.evil.example.com` and `https://localhost@evil.example.com` read as remote; missing/unparseable fails closed; `host.docker.internal` deliberately excluded (nothing in `test.yml` or `playwright.config.ts` needs it, and it resolves to a different machine). **Adversarial review of the first attempt found it did not work in the shipped artifact:** it read `process.env.NEXT_PUBLIC_SUPABASE_URL`, which Turbopack inlines at build time, so the compiled gate was a frozen literal (`new URL("https://<project>.supabase.co")` in the emitted chunk) while `createAdminClient()` — via `clientEnv`, which returns raw `process.env` under `SKIP_ENV_VALIDATION`, and `bun run build` sets it — was a live read. An artifact built against loopback, deployed off-Vercel with `E2E_DEV_LOGIN=1` and runtime env pointing at the hosted project, was a real bypass. Closed structurally rather than patched: the gate and both `createClient`/`createAdminClient` now resolve the URL through one accessor, `getSupabaseUrl()` in `src/lib/env.ts`, so they cannot disagree about which database is about to be touched under any build/runtime env skew. Verified in the built output rather than assumed — the gate in the emitted chunk no longer contains a Supabase literal. Same commit: the Vercel floor was inverted from deny-`production`/`preview` to deny-anything-not-known-safe, so an unrecognised `VERCEL_ENV` fails closed instead of falling through; dead `"::1"` dropped from the loopback set (`new URL().hostname` only ever yields the bracketed form, every bare spelling throws); and the docstring's absolute claims ("the database holding real data is never reachable through this path") were replaced with what is actually true — loopback constrains the network path, not the data, so a self-hosted Supabase/Kong, a sidecar, an SSH tunnel or a local reverse proxy all satisfy it in front of a real database. Also corrected the wrong premise that `next build`/`next start` "force `NODE_ENV=production`": they do not (`node_modules/next/dist/bin/next` does `NODE_ENV = NODE_ENV || defaultEnv`, a default with a warning); the artifact is safe because a production build constant-folds the `NODE_ENV` branch out entirely — `NODE_ENV` appears zero times in the emitted route chunk. The `NODE_ENV === "development"` path is deliberately **not** narrowed: it is the wider hole (any host serving via `bun dev` against a hosted project hands out uncredentialed admin) but it is pre-existing behavior and restricting it is the repo owner's call, so it is documented as an accepted exposure and filed as #679 (`bug`, `needs-human`) with the exact reachable combination. Route-gate suite 31 → 42 tests, plus a new `src/lib/supabase/__tests__/server-url-source.test.ts` (3 tests) pinning that both server clients read the shared accessor; all 12 new cases red-checked against the pre-fix code (9 + 3 failures with the fix reverted). Honest limit: these tests import the module unbundled, where every `process.env` read is live, so no unit test in this suite can observe build-time inlining — the compiled-chunk grep is the only evidence for that half, and it is recorded in PR #678. Still open by design: the route upserts `roles: ["admin"]`, which the E2E specs depend on — narrowing that is a separate decision.
