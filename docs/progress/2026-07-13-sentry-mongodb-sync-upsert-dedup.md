- **2026-07-13 (MongoDB sync duplicate-key upsert fix — branch `sentry-fix/SENTRY-7542174707`; Sentry MGR-A, issue 7542174707).** `upsertRows()` in `src/integrations/mongodb/sync.ts` — the shared helper every MongoDB→Postgres sync entity funnels through — sent each 50-row chunk straight to a single Supabase `.upsert(batch, { onConflict })` call, which compiles to one `INSERT ... ON CONFLICT DO UPDATE` statement. Postgres rejects that whole statement with "ON CONFLICT DO UPDATE command cannot affect row a second time" if two rows in it share an onConflict-column value; `beer_styles`/`brands`/`vessels` upsert on `name`, and the legacy Mongo collections have no uniqueness guarantee there, so duplicate-name documents reliably failed an entire chunk (up to 50 rows) on every sync run. Fix: added `dedupeByConflictKey()`, which keeps the last row per conflict-key value before chunking (rows missing the onConflict column, e.g. `recipes` which upserts with no explicit `id`, pass through untouched rather than exempting the whole batch) and logs a warning with the dropped count. Regression test in `src/integrations/mongodb/__tests__/sync.test.ts` reproduces the exact Postgres error via a mock `.upsert()` responder and confirms it's gone post-fix (verified failing pre-fix, passing post-fix). Gates: typecheck + lint clean, 148 files/2224 tests green.
