- **2026-07-14 (SENTRY-7542174707 re-triage — observability gap in MongoDB sync upsert-error logging; branch `sentry-fix/SENTRY-7542174707`).** Sentry issue MGR-A ("Upsert error for %s batch %d: %s") kept firing after the 2026-07-13 duplicate-key dedup fix (PR #395), so it was re-triaged rather than assumed already resolved. Classification: **(D) observability gap**, not a recurrence of the original bug — `logger.error("Upsert error for %s batch %d: %s", table, batchIndex, error.message)` in `src/integrations/mongodb/sync.ts` is a pino printf-style call, but `src/lib/logger.ts`'s `forwardToSentry()` only recognized three call shapes (`Error` instance, `{err, ...ctx}` + message, bare string) and forwarded a printf template's *raw, un-interpolated* string to `Sentry.captureMessage()` — dropping the table name, batch index, and actual Postgres error message on every event, which is exactly why this session's stack trace was `(unavailable)` and the event context was empty. Fix: `forwardToSentry()` now detects printf-style calls (string first arg with `%s`/`%d`/etc. placeholders plus extra args) and interpolates them via `node:util`'s `format()` before forwarding, attaching the raw args as `extra` — a self-contained fix in the shared logging helper that also covers every other printf-style `logger.error`/`logger.fatal` call site in the repo (email.ts, mongodb/client.ts, settings/api-key/route.ts) without touching those files. Additionally upgraded the two call sites this issue actually traces to (`upsertRows()`'s upsert-error branch and `syncPhase()`'s catch block) to structured `logger.error({ err, ...ctx }, "message")` calls, routing through the pre-existing `instanceof Error` branch to get `Sentry.captureException` with a real stack trace instead of just a message. Two regression tests added (`src/lib/__tests__/logger.test.ts` — printf interpolation; `src/integrations/mongodb/__tests__/sync.test.ts` — structured error-logging call site), both confirmed failing pre-fix (via `git stash` of the respective source file) and passing post-fix. Full suite (159 files / 2358 tests), typecheck, and lint all clean. **This is not a resolution of the underlying error** — the Postgres upsert failure that is still recurring in production after the 2026-07-13 fix remains undiagnosed; only its reporting is fixed. An investigation issue was opened for the still-unknown root cause, to be re-triaged once the next production event arrives with real diagnostic content.
